# --- test_asyncio, one SUBMODULE at a time --------------------------------
#
# CPython's test_asyncio is a 41-file, 31k-line PACKAGE, and naming the package
# here would score 0 tests: the driver discovers unittest.TestCase subclasses
# defined in ONE named module (test._grail_harness >> score), and the package's
# __init__.py defines none.  Naming submodules works instead -- the driver
# resolves any dotted name through importlib ___moduleNameToPath___ -- which is
# what makes this corpus adoptable incrementally rather than all at once.
#
# The split that decides the order is test_asyncio/utils.py.  22 of the 38 test
# files import it, and it needs selectors, socketserver, threading,
# unittest.mock, http.server, wsgiref.simple_server, and three asyncio
# submodules Grail does not have (base_events, format_helpers, log).  The other
# 16 need only unittest.IsolatedAsyncioTestCase, which is a 158-line port --
# and that is ~4,950 lines of upstream tests for the primitives that are next
# anyway (locks 1825, taskgroups 1118, queues 725, timeouts 411, waitfor 353).
#
# test_context is first because it is the smallest (38 lines) and needs
# NEITHER: plain unittest.TestCase, and only gather/sleep/run from asyncio. It
# is here to prove the mechanism end to end, and it is expected to SKIP --
# decimal.HAVE_CONTEXTVAR is False because Grail's decimal shares one module
# global, so upstream's skipUnless is doing its job rather than being dodged.
test.test_asyncio.test_context
# test_waitfor is the first REAL exercise of IsolatedAsyncioTestCase: 353 lines
# of upstream wait_for / shield / cancellation tests, all of them async methods
# on that class.  The one asyncio name it needs and Grail lacks is
# ``asyncio.wait``, used once, so the tests that route through it fail and the
# rest are a genuine baseline rather than a skip.  (``asyncio.timeout`` appears
# in the file only inside a comment.)
test.test_asyncio.test_waitfor
# test_locks is the payoff of porting IsolatedAsyncioTestCase: 1,825 lines
# grading Lock / Event / Condition / Semaphore / BoundedSemaphore / Barrier,
# all vendored from upstream rather than written here.  75 tests, 64 passing.
#
# It earned its place immediately by finding TWO runtime bugs no test in this
# tree had reached -- ``async with'' not suspending on a blocking __aenter__
# (so a contended Lock ran its body unlocked), and cancel(msg=...) losing the
# message.  Both fixed; see AsyncWithAst >> ___awaitPrefix___ and
# Future >> _make_cancelled_error.
#
# The 11 that remain are four separate things, none of them the locks:
#   * 4 need asyncio.wait / asyncio.timeout / asyncio.TaskGroup, which do not
#     exist yet;
#   * 3 assert that ``await <non-awaitable>'' raises TypeError, which Grail
#     deliberately does not (CoroutineSuspensionTestCase pins the deviation);
#   * 2 pin CPython's exact TypeError wording ("Lock.__init__() got an
#     unexpected keyword argument 'loop'"), a tree-wide message-format gap;
#   * 2 want the SAME exception instance out of a cancelled task, and Grail
#     copies an already-signalled exception when it crosses a Task boundary --
#     measured for ValueError too, so it is the raise machinery, not asyncio.
test.test_asyncio.test_locks
#
# asyncio.queues, vendored VERBATIM -- the first of these files that needed no
# adaptation at all.  59 tests, 51 passing, and all 8 failures are the single
# missing name asyncio.TaskGroup, so no queue behaviour is unaccounted for.
#
# It paid for itself twice over outside asyncio, both times on a name bound to
# something that looked right from Grail's own tests:
#   * asyncio.TimeoutError was a class of Grail's own where upstream aliases the
#     BUILTIN (since 3.11).  Correct at the raise site, wrong at every catch
#     site, and missing the builtin's descent from OSError.
#   * types.GenericAlias was a five-line stub SHADOWING Grail's real
#     PyGenericAlias.  Declaring no __init__, it accepted
#     ``__class_getitem__ = classmethod(GenericAlias)'' and answered an
#     attribute-less object -- a silent wrong answer, not an error.
test.test_asyncio.test_queues
#
# asyncio.taskgroups, vendored verbatim.  96 tests: 84 passing, 12 skipped,
# ZERO failures -- the module scores OK.
#
# It was 40 passing, and the 48-failure block was ONE missing name: the module
# reruns its whole suite as TestEagerTaskTaskGroup under
# loop.set_task_factory(asyncio.eager_task_factory), and Grail had neither the
# factory nor eager start.  Clearing it took three changes, none of which was
# sufficient alone: eager_task_factory + Task(eager_start=...), a
# loop.create_task that actually CONSULTS the task factory it had been storing
# and never reading, and an attribute-path fix for the shadowing
# @staticmethod the factory is (the reader INVOKED it and returned its value,
# so the caller's own () met a non-callable).
#
# The two classes now fail on exactly the same 7 tests, which is the useful
# invariant: there is no eager-specific failure left, so anything below is
# about TaskGroup itself and will move for both at once.
#
# Vendoring it took test_queues from 51/59 to 59/59 (every one of its remaining
# failures was the missing TaskGroup) and found two bugs OUTSIDE asyncio:
#   * a ``with'' whose __exit__ raised had __exit__ called a SECOND time, with
#     its own exception -- the clean-path call was emitted inside the try whose
#     handler calls __exit__ again.  Plain ``with'' had it too.
#   * BaseExceptionGroup never narrowed to ExceptionGroup (PEP 654), so the
#     ordinary ``except ExceptionGroup'' caught nothing.
#
# What closed the last 7 per class:
#
#   * 6 are the refcycle family (test_exception_refcycles_*), now SKIPPED
#     EXPLICITLY in cpython_suite_skips.txt rather than counted as failures.
#     They assert CPython refcounting properties -- gc.get_referrers, and a
#     weakref that must be dead by a given statement -- and reach them through
#     a coro's cr_frame.  Both halves are CPython memory-model facts, not
#     asyncio behaviour; see that file for what the skip stops covering.
#   * 1 was test_taskgroup_task_context, which needed REAL contextvars: it
#     passes an explicit ``context=`` to create_task and then reads a
#     ContextVar back OUT of that context object afterwards.  contextvars was
#     a single global slot, so ``context=`` had nothing to select between and
#     asyncio did not plumb it anywhere.  Both are now real.
#
# Two entries that used to be on this list are gone.  "1 needs
# asyncio.timeout" was closed by vendoring asyncio/timeouts.py.  "1 mixes
# asynccontextmanager with nested groups (undiagnosed)" was
# test_taskgroup_context_manager_exit_raises, and the diagnosis, once looked
# at, was not about nesting at all: contextlib.asynccontextmanager was a
# two-line pass-through returning the UNDECORATED function, so ``async with
# database():`` met a bare async_generator and raised TypeError -- missed
# __aexit__.  Under the TaskGroup that became a group whose single child was
# a TypeError, which ``except* CustomException'' rightly declined to catch.
# Worth remembering as a diagnostic pattern: an ExceptionGroup carrying the
# WRONG child type is a report about the child, not about the group.
#
# NOTE: test/test_asyncio/utils.py is vendored PARTIALLY -- see the header in
# that file.  test_taskgroups imports one 13-line function from it, and the real
# 609-line version needs wsgiref (~1,090 lines) and a BaseEventLoop to subclass.
test.test_asyncio.test_taskgroups
