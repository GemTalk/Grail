# Explicit shard placement for the SUnit gate's heaviest test classes.
# ONE LINE PER CLASS: '<ClassName> <shardIndex>'.  Everything not listed keeps
# the default char-sum placement in tests/scripts/runTestsShard.gs.
#
# WHY OVERRIDES AND NOT A COST-BALANCED PARTITION.  Balancing the whole suite
# by measured per-class cost was tried and made the gate SLOWER (max shard 38s
# -> 38s, having predicted 19s).  Per-class costs are not additive: classes
# share framework imports, so a bin-packer that treats them independently
# scatters co-located ones and every shard re-pays the import.  It put twilio
# on three shards out of four.
#
# So the default stays the char-sum hash -- which preserves whatever
# co-location the suite already has -- and only a few SELF-CONTAINED heavy
# classes are placed by hand.  Each listed class is the sole expensive user of
# its imports, so moving it moves its whole cost and splits nothing.
#
# Correctness does not depend on any of this: every class lands on exactly one
# shard whatever the file says.  An index outside 0..N-1 is ignored (the gate
# can run with fewer workers than the file assumes).  Delete the file and the
# suite still runs, just less evenly.
#
# THIS FILE GOES STALE, and the first version of it did.  It was written when
# the whole gate was ~38s and it emptied shard 0 by moving work ONTO it; the
# suite then roughly tripled and the classes that had grown were the ones it
# had piled there, so shard 0 became the slowest by a factor of nearly three.
# The numbers below are a snapshot, not a rule -- re-measure before trusting
# them.
#
# HOW TO RE-MEASURE.  Per-class timings come from a normal gate run under
# GRAIL_TEST_TIME_CLASSES=1, which makes each shard emit one
# GRAIL_CLASS_TIME|<shard>|<class>|<ms>|<tests> line per class:
#
#   GRAIL_TEST_TIME_CLASSES=1 ./scripts/run_tests.sh
#   cat out/shard_*.out | grep ^GRAIL_CLASS_TIME | \
#     awk -F'|' '{printf "%6.1fs shard %s %s\n", $4/1000, $2, $3}' | sort -rn
#
# The per-shard totals are on the GRAIL_SHARD_RESULT lines (ms=) and in
# run_tests.sh's "per shard (concurrent)" TIMING line.  They matter because CI
# runs the four shards as TWO jobs of two concurrent shards each, so a job
# costs its SLOWEST shard -- reassigning whole shards between jobs cannot help,
# only evening out the four shards can.
#
# Measured, four shards concurrent, canonical classes on (2026-08-18, macOS
# arm64 / GemStone 4.0, 4885 tests green throughout):
#     before  125.1s  80.5s  71.1s  45.7s   jobs 125.1s / 71.1s, gate 136s
#     after    77.4s  77.2s  82.4s  79.6s   jobs  77.4s / 82.4s, gate  86s
# Ideal is total/4 = 79.1s, so the slowest shard is now 4% off the floor and
# there is nothing left to win by moving classes around.
#
# On CI (ubuntu-22.04, 4-CPU, 3.7.5, two concurrent shards per job), before,
# then two consecutive runs of the SAME code after:
#     before   shard phase 303s / 149s   jobs 324s / 169s
#     after 1  0=172s 1=186s | 2=171s 3=188s   phase 187s / 189s
#     after 2  0=145s 1=166s | 2=230s 3=249s   phase 167s / 251s
#
# DO NOT READ A JOB PAIR AS A BALANCE MEASUREMENT.  Run 1 landed the two jobs
# 1% apart and run 2 landed them 1.5x apart, on identical work -- GitHub's
# hosted runners differ enough that a job's whole shard phase moves +-35%.
# Reading run 1 alone would have credited the rebalance with more than it did;
# reading run 2 alone would look like the original skew had come back.
#
# What IS stable is the difference between two shards ON THE SAME RUNNER,
# because they share a machine:
#     shard 1 - shard 0:  +14s, +21s
#     shard 3 - shard 2:  +17s, +19s
# Roughly 10%, in both runs.  That is the number this file can act on, and it
# says the partition is even.  Cross-runner comparisons cannot be, so a future
# re-measurement should either compare within a runner or use the local
# all-four-shards run above, where one machine times all four.
